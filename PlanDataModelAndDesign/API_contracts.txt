1. AUTHENTICATION PROVIDERS SERVICE
Endpoint: /api/auth-providers
-------------------------------------------------------------------------------

[POST /api/auth-providers]
- Description: Creates a new authentication source (e.g., Google, GitHub, Internal).
- Request Body:
  {
    "name": "string"
  }
- Success Response (201 Created):
  {
    "id": 1,
    "name": "string"
  }
- Error Response (400 Bad Request):
  {
    "error": "Provider name already exists or invalid data"
  }

[GET /api/auth-providers]
- Description: Lists all registered authentication providers.
- Success Response (200 OK): Array of provider objects.

-------------------------------------------------------------------------------
2. ROLES SERVICE
Endpoint: /api/roles
-------------------------------------------------------------------------------

[POST /api/roles]
- Description: Registers a new system role for access control.
- Request Body:
  {
    "name": "string",
    "description": "string"
  }
- Success Response (201 Created): Role object with generated ID.

[PUT /api/roles/{id}]
- Description: Updates the name or description of an existing role.
- Request Body:
  {
    "name": "string",
    "description": "string"
  }
- Success Response (200 OK): Updated role object.

-------------------------------------------------------------------------------
3. USERS SERVICE
Endpoint: /api/users
-------------------------------------------------------------------------------

[POST /api/users]
- Description: Registers a new user. Passwords are hashed via Bcrypt (12 rounds).
- Request Body:
  {
    "name": "string",
    "email": "user@example.com",
    "password": "plaintext_password",
    "provider_id": integer,
    "external_id": "string_uid"
  }
- Success Response (201 Created):
  {
    "id": 1,
    "name": "string",
    "email": "user@example.com",
    "provider_id": 1,
    "external_uid": "string_uid",
    "created_at": "ISO-TIMESTAMP",
    "updated_at": "ISO-TIMESTAMP"
  }
- Security Note: "password_hash" is strictly omitted from all responses.

[POST /api/users/assign-role]
- Description: Links a user to a specific role in the junction table.
- Request Body:
  {
    "users_id": integer,
    "roles_id": integer
  }
- Success Response (200 OK):
  {
    "message": "Role assigned successfully"
  }

[GET /api/users/{id}/profile]
- Description: Retrieves full user profile including Role and Auth Provider details.
- SQL Logic: JOINs users, roles_users, roles, and auth_providers.
- Success Response (200 OK):
  {
    "id": 1,
    "name": "string",
    "email": "string",
    "role_name": "Admin",
    "provider_name": "Internal",
    "created_at": "ISO-TIMESTAMP"
  }

-------------------------------------------------------------------------------
4. OPERATIONAL WORKFLOW: CREATING AN ADMIN USER
-------------------------------------------------------------------------------
To establish a user with Admin privileges, the following sequence is required:

STEP 1: Create/Identify Auth Provider
  Call [POST /api/auth-providers] -> Get "provider_id"

STEP 2: Create/Identify Admin Role
  Call [POST /api/roles] { "name": "Admin" } -> Get "roles_id"

STEP 3: Create User Account
  Call [POST /api/users] -> Get "users_id"

STEP 4: Finalize Privilege Assignment
  Call [POST /api/users/assign-role] using "users_id" and "roles_id"

5. TASKS SERVICE
Endpoint: /api/tasks
===============================================================================

[List Active Tasks]
- Endpoint: GET /api/tasks
- Controller: getTasks(req, res)
- Success Response (200 OK):
  [
    {
      "id": 1,
      "title": "Setup Database Server",
      "description": "PostgreSQL configuration for ArtHup ecosystem",
      "category_id": 5,
      "status": "OPEN",
      "priority": "HIGH",
      "is_active": true,
      "created_at": "2026-03-17T18:00:00Z"
    }
  ]

[Create New Task]
- Endpoint: POST /api/tasks
- Controller: createTask(req, res)
- Business Rules:
  - title: required, minimum of 10 characters.
  - status: cannot be initialized as COMPLETED.
  - priority: if description contains "URGENT", it will be forced to HIGH.
- Request Body:
  {
    "title": "Develop API Integration",
    "description": "CRITICAL task for the marketplace",
    "category_id": 2,
    "priority": "LOW"
  }
- Success Response (201 Created): returns created object with adjusted priority.
- Error Response (400 Bad Request): short title or non-existent category.

[Update Task]
- Endpoint: PUT /api/tasks/{id}
- Controller: updateTask(req, res)
- Business Rules:
  - Immutability: if status = COMPLETED, title and category_id cannot be modified.
  - Logical Cascade: if is_active = false, all linked task_schedules will have end_date = NOW().
- Request Body (partial):
  {
    "status": "IN_PROGRESS",
    "priority": "MEDIUM"
  }
- Success Response (200 OK): update successful.
- Error Response (404 Not Found): non-existent ID.
- Error Response (400 Business Rule Violation): attempt to edit archived task without reactivation.

[Remove / Archive Task]
- Endpoint: DELETE /api/tasks/{id}
- Controller: deleteTask(req, res)
- Business Rules:
  - Hard Delete: if status = OPEN and description empty → permanent deletion.
  - Soft Delete Cascade: if content/progress exists → set is_active = false and terminate schedules.
- Success Response (200 OK):
  {
    "id": "15",
    "action": "SOFT_DELETE_CASCADE",
    "message": "Task and all associated schedules archived."
  }
- Error Response (400 Business Rule Violation): attempt to delete task with COMPLETED status.

-------------------------------------------------------------------------------
HTTP STATUS CODES SUMMARY
-------------------------------------------------------------------------------
200 OK - Successful operation (Read, Update, Delete)
201 Created - Resource created successfully
400 Bad Request - Business rule violation
404 Not Found - Resource not found
500 Internal Error - Database connection failure or unexpected error
